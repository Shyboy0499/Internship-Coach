# Message Templates

Starting points, not scripts. Adapt each one to the intern's voice, the channel, and the details they gave you — a template that reads like a template undermines it. Fill every `[bracket]` from context, or ask for what's missing. Keep chat messages short; mentors skim.

## Asking for help when stuck

```
Hi [Name] — I'm stuck on [task] and could use a pointer when you have a few minutes ([not urgent / it's blocking me]).

Goal: [what you're trying to do]
Tried: [1–3 things, and what you ruled out]
What happens: [exact error / output / point of confusion — paste or screenshot]
My guess: [hypothesis, or what you'd try next]
```

## Clarifying a new task (repeat-back)

For a bigger task, start from the full task brief in `delivering-work.md`.

```
Thanks! To make sure I build the right thing:
- Goal: [the task in your own words]
- Done looks like: [deliverable and format]
- Due: [date] — is this higher or lower priority than [other task]?
- I'm planning to start by [first step]. Does that sound right?
```

## End-of-day update

```
EOD update
Done: [what you finished or moved forward]
Next: [what you'll do tomorrow]
Blocked / risks: [none — or the blocker and what you need]
```

## Weekly update

```
Week [N] update — [project]
Shipped / progress: [2–4 bullets, outcomes over activity]
Learned: [one thing]
Next week: [2–3 bullets]
Risks / needs from you: [none — or specific asks]
```

## Flagging a delay or risk

```
Heads-up on [task]: it's going to take longer than I estimated. [One-line reason.]
New estimate: [date].
Options: (a) [cut scope], (b) [move the date], (c) [get help from X].
I'd lean toward [option] — what do you think?
```

## Owning a mistake

If IT, security, or the team's on-call is involved, contact them first — `when-something-breaks.md` has who to tell and a helpdesk template.

```
[Name], I made a mistake I want to flag right away: [what happened, plainly].
Impact: [who or what is affected, as far as I know].
What I've done so far: [containment steps].
Proposed fix: [plan] — should I go ahead, or would you rather handle it differently?
Going forward: [what you'll do to prevent it].
```

## 1:1 agenda

```
1:1 — [date]
1. Progress since last time: [1–2 lines]
2. Blockers / decisions I need: [...]
3. Questions: [batched list]
4. Feedback ask: [one specific question]
5. (Optional) Learning or career question: [...]
Action items from last time: [status of each]
```

## Asking for specific feedback

```
Could I get your quick take on [specific piece of work]? In particular: [one or two concrete questions — e.g. "was the level of detail right for your manager?" / "is there a cleaner way to structure this?"].
Totally fine to tell me what to do differently next time.
```

## Asking for more work

```
I've wrapped up [task] ([link]). I have capacity for more — I could [option A] or [option B], or is there something more useful for the team right now?
```

## Closing the loop

```
Following up on [problem/suggestion] — [what you did], and it worked / it's done. Thanks for the pointer!
```

## Pre-start email to a mentor or manager

```
Subject: Looking forward to starting on [date]

Hi [Name],

I'm [Your name], joining [team] as a [role] intern on [start date]. I'm excited to get started.

Is there anything you'd recommend I read, learn, or set up before my first day? I've been [brief prep you're already doing — e.g. reviewing the team's public docs / brushing up on SQL].

Also, is there anything I should know about logistics for day one (time, location or setup, who to ask for)?

Thanks, and see you soon,
[Name]
```

## Midpoint self-review

```
Midpoint self-review — [Name], [date]

Goals from the start of the internship: [list, with status for each]
What I've delivered: [outcomes, with links or numbers where possible]
What I've learned: [skills, tools, domain knowledge]
Feedback I've received and how I applied it: [1–3 examples]
Where I want to grow in the second half: [1–2 areas]
Plan for the remaining weeks: [milestones]
Questions for you: Am I on track? What would make the rest of my internship a clear success?
```

## Work log ("brag doc")

Add a few lines every Friday — it makes the midpoint review, final presentation, and resume almost write themselves.

```
Week of [date]
- Did: [task] → Result: [outcome, number, or who it helped]
- Learned: [...]
- Feedback received: [...]
- Thanks owed to: [person, for what]
```

## Final presentation outline

For story, slides, rehearsal, and Q&A, see `presenting.md`.

Aim for 8–12 minutes plus questions. Rehearse once with the mentor if possible.

```
1. Who I am and what I worked on (1 slide)
2. The problem and why it matters to the team or the business (1–2 slides)
3. What I built or found (2–4 slides — show it: demo, chart, before/after)
4. Impact (numbers, users helped, time saved — honest, even if modest)
5. What I learned (1 slide)
6. What's next / handoff (1 slide)
7. Thank-yous (name the people who helped)
```

## Handoff doc

```
[Project] — handoff
What it is: [2–3 sentences]
Where it lives: [repos, docs, dashboards, files]
How to run or use it: [steps]
Current state: [done / partially done / known issues]
Open questions and next steps: [...]
Who knows the most about it after I leave: [names]
```

## Return-offer conversation

For how decisions are made, what to do with the answer, and reference requests, see `return-offer.md`.

Raise it around the midpoint, not only in the last week.

```
I've really enjoyed working on [team/project] and I'd love to come back after graduation. Could we talk about what a return offer looks like here, and whether I'm on track? Is there anything you'd want to see from me in the remaining weeks?
```

## End-of-internship thank-you

```
Hi [Name] — as my internship wraps up, I wanted to say thank you. [One specific thing they did and what it meant — e.g. "Walking me through the deploy pipeline in week 2 saved me days."] I learned a lot about [area], and I'd love to stay in touch.
[If appropriate:] Would you be comfortable being a reference for me in the future?
```

## Resume bullets from the internship

Build these from the work log or notebook — real outcomes only, never invented numbers. One line each: **action verb + what you did + measurable result**, with the tools named where they matter.

Give finished bullets first, using only the facts the intern provided, so they can paste them straight in. Then, separately, point out where a real number they could look up would make a bullet stronger.

Worked example — what the intern said: "I built a dashboard the support team uses every morning, automated a weekly report that took my manager about 3 hours, and presented a refund analysis that led to a policy change."

Finished bullets (no brackets, nothing added that they didn't say):

```
- Built a dashboard the support team now uses every morning to start their day.
- Automated a weekly report in Python, saving my manager about 3 hours of manual work each week.
- Analyzed refund requests and presented findings to operations leads, leading to a change in the refund policy.
```

Then, separately: "If you know how many people use the dashboard, or what the policy change achieved, adding that number would make these stronger."

If the real numbers are confidential, use relative terms ("cut processing time by about 90%", "3x faster") and check with the manager what's fine to share. Never include customer data, unreleased figures, or internal project code names without permission.

## Interview stories (STAR)

Prepare three to five stories from the internship for future interviews and the return-offer conversation. Good candidates: a project win, a mistake and how you recovered, acting on tough feedback, getting unstuck on something hard, working across a team.

```
Title: [short name for the story]
Situation: [the context, in one or two sentences]
Task: [what you were responsible for]
Action: [what *you* did — specific steps, decisions, and why]
Result: [the outcome, with a number if possible]
Learned: [what you'd do the same or differently next time]
```

Keep each story to about two minutes spoken. "I" for your own actions, "we" only for genuinely shared work.

## Pull request description (software interns)

Keep the PR small enough to review in one sitting. Self-review the diff and run the tests before requesting review.

```
## What
[One or two sentences on what this change does.]

## Why
[The problem or ticket it addresses — link it.]

## How
[Key decisions and anything non-obvious. Mention alternatives you considered if relevant.]

## Testing
[What you ran and what you checked — tests added, manual steps, screenshots.]

## Questions for reviewer
[Anything you're unsure about — reviewers appreciate being pointed at it.]
```
